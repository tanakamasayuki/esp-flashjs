# トラブルシューティング

[English](./troubleshooting.md) · **日本語**

症状から引けるようにしてあります。手元にあるのは症状だからです。ここに書いてあることのほとんどは実機で見つけたもので、いくつかは**もっともらしい説明のほうが間違っていた**ために載っています。

このページのどの項目よりも役に立つ習慣が2つあります。

- **要約ではなくエラー本文を読む。** ESP32 のフラッシュ周りのツールは、具体的な失敗を「失敗しました」の一語に潰しがちです。具体的な失敗はたいてい手の届くところにあります
- **esptool と比較する。** esptool はこのライブラリとコードを共有していません。両者が一致すればそれは証拠であり、食い違えばどちらかに探す価値のあるバグがあります

## ブラウザがデバイスを認識しない

**ポート選択ダイアログが出ない、または `WebSerialTransport.isSupported()` が false。**

Web Serial には3つの条件があり、**どれが欠けても同じように失敗します**。

| 条件 | 欠けたときの症状 |
| --- | --- |
| Chromium 系の**デスクトップ**ブラウザ | Firefox と Safari は Web Serial 未実装。Android / iOS の Chrome も同様 |
| **セキュアコンテキスト**（HTTPS か `localhost`） | `file://` で開くと失敗。localhost 以外の平文 HTTP も同様 |
| **ユーザー操作** | クリックハンドラ外の `requestPort()` は拒否される |

汎用のエラーを出さず、**どれが欠けているかを名指し**してください。Firefox のユーザーと `file://` のユーザーでは、必要な案内が違います。

**ダイアログは出るがボードが一覧に無い。** これはブラウザではなくドライバの問題です。まず OS レベルでポートが見えているか確認してください（`ls /dev/tty*`、Windows ならデバイスマネージャ）。

## 接続に失敗する・チップが認識されない

**`connect()` が例外を投げる、または `loader.chip` が null のまま。**

### 別のものがポートを掴んでいる

シリアルポートは共有できません。2つのプロセスが同じポートを読むと互いの応答を食い合い、**壊れたデバイスや不良ケーブルとそっくりな症状**になります。最も多い原因であり、最も簡単に除外できます。

```sh
fuser -v /dev/ttyUSB0        # Linux
lsof /dev/tty.usbserial-*    # macOS
```

IDE で開きっぱなしのシリアルモニタも該当します。ハングした `esptool` も同様です。

### ボードがブートローダに入っていない

`connect()` は DTR と RTS を操作してチップをダウンロードモードに落とします。多くの開発ボードはこれを前提に配線されています。その回路が無いボードでは手動が必要です。BOOT を押しながら EN を叩き、BOOT を離してから `{ autoReset: false }` で接続してください。

`canAutoReset(transport)` はそもそもそれらの線を駆動できるかを返すので、UI はユーザーがどちらの状況にいるかを説明できます。

### 応答は届いているが捨てられている

**試したすべてのボードで**チップ検出が失敗するなら、ボードではなく Transport を疑ってください。下層の read とタイムアウトを競走させる Transport は、タイムアウトが勝ったときに進行中のチャンクを放棄します（キャンセルされるのではなく、捨てられます）。結果として以降のフレームが1つずつずれ、**「不明なチップ」という、タイムアウトとの関連が見えない症状**になります。

`WebSerialTransport` がバックグラウンドポンプで読んでいるのはこのためです。自作の Transport なら [transports.ja.md](./transports.ja.md#間違えやすいところ) を参照してください。

## stub が読み込めない

**`loadStub()` が false を返し**、以降の読み出しが `REQUIRES_STUB` を投げる。

警告のメッセージに、以下のどれだったかが出ています。

### `could not fetch …` — ブラウザではない

`fetchStub` はモジュール隣の URL を `fetch()` に渡します。Node の fetch は `file:` スキームを実装していないので、**ブラウザ外では原理的に動きません**。自分で `registerStub` にイメージを渡してください（[guide.ja.md §12](./guide.ja.md#12-ブラウザ以外で使う)）。

チップ名のリストではなく、`dist/stub/` の **全 JSON** を登録してください。その理由が次項です。

### `expected "OHAI" from the stub, got …` — このシリコンには別の stub が要る

stub の転送は成功し、チップはそこへ飛びましたが、何も返ってきません。ほぼ確実に、**その個体には存在しないアドレス**に stub を書いています。

**実際に流通しているのは v3.0 未満の ESP32-P4 です。** RAM の位置が異なり `esp32p4-rev1` が必要です。現在流通している P4 はすべて v3.0 未満なので、その stub を持たないビルドは**このファミリで一切動きません**。ライブラリは eFuse からリビジョンを読んで選びますが、チップ名で stub を登録する手組みの Node 環境はこれを取りこぼします。

### `Secure Download Mode` — チップが意図的に拒否している

Secure Download Mode は stub が必要とするコマンドを無効化します。異常ではなく、そう設定されたデバイスです。この状態で読み出しは不可能で、書き込みは可能な場合があります。

## 読み出しが失敗する・短く返る

**`flash read checksum mismatch: expected 4096 bytes, got 4092`**、または途中でタイムアウトする。

リンクがバイトを落としています。これは通常の意味で「速度が速すぎる」のとは違い、**リトライで抜けられる種類の破損でもありません**。

`READ_FLASH` の1転送は **all-or-nothing** です。stub は範囲全体に MD5 を1つ返すので、1バイト落ちれば全部が破棄されます。100KB に1バイト落とすリンクで 4MB を読むのは、何回試行しても完了しません。

**一度に要求する量を減らしてください。** 効くのはそれだけです。

```js
await flash.read(offset, size, { chunkSize: 0x8000 });   // 32KB ずつ
```

同梱ツールも同じことをします。`tools/fixture-device/capture.sh` は失敗が続くとチャンクを半分に縮め、`tools/hardware-check.mjs` は `--chunk` を受け取ります。

### そのうえで速度を変える。ただし仮定せず測る

**遅いほうが安全とは限りません。** ある CH340 ボード（USB パススルー経由）で 256KB の読み出しを各速度4回:

| baud | 成功 |
| --- | --- |
| 115200 | 2/4 |
| 230400 | 1/4 |
| **460800** | **4/4** |
| 921600 | 0/4 |
| 1500000 | 0/4 |

115200 は 460800 より**遅く、かつ不確実**でした。しかもこの順位は別のケーブルやホストには持ち越せません。測ってください。

```sh
for b in 115200 230400 250000 460800 500000 750000 921600 1500000; do
  esptool --port "$PORT" --baud $b read-flash 0x0 0x40000 /tmp/t.bin >/dev/null 2>&1 \
    && echo "$b ok" || echo "$b FAILED"
done
```

64KB ではなく 256KB で測ってください。小さい読み出しなら通る速度が、1MB を超えると崩れます。

### ライブラリを容疑から外す

同じ読み出しを esptool で実行します。esptool も失敗するなら、リンクの問題です。

```sh
esptool --port "$PORT" --baud 460800 read-flash 0x290000 0x50000 /tmp/t.bin
```

### 仮想マシンを使っている場合

USB パススルー（WSL2 の usbipd、VM の USB 転送）は、直結よりはるかにバイトを落とします。該当するか確認できます。

```sh
ls -l /sys/class/tty/ttyUSB0/device/driver     # vhci_hcd 配下なら usbip
```

ホスト側で読み出してファイルを持ち込むほうが、パススルーを調整するより速く確実です。

## 読めるがデータがおかしい

**同じ領域を2回読むと違う**、またはデバイスが確かに書いたはずのデータをパーサが拒否する。

まず同じ領域を2回読んで比較してください。**違うならリンクの問題**です（前節へ）。一致するならバイト列はデバイスが保持しているものであり、問題は「それが何を意味するか」です。

### 読み出しの合間にデバイスが書き換えた

アプリケーションは動作中にフラッシュへ書きます。とくに NVS は起動のたびに消去済みエントリが溜まり、ページの seqNo が進みます。1時間前に取得したパーティションは、**何も異常が無くても**バイト一致しません。バイトではなく**内容**で比較してください。

```js
const before = parseNvs(fixture);
const after = parseNvs(justRead);
console.log(diffNvs(before, after));    // 空なら意味のある変化は無い
```

### パーティションが名乗る形式と中身が違う

`spiffs` という名前のパーティションに LittleFS が入っていることがあります。ESP-IDF の LittleFS は歴史的経緯でパーティションラベルの既定が `"spiffs"` なので、パーティションを名指しせずに両方をマウントするスケッチは**一方が他方を上書きします**。症状は「`spiffs` はデータで埋まり、`littlefs` は全部 `0xFF`」です。

オフセット8を見てください。そこに `littlefs` という文字列があれば、ラベルが何であれ LittleFS のスーパーブロックです。

## 空でないはずのパーティションが空に見える

**ファイルシステムや NVS のパーティションが、ファイル0件・エントリ0件で解析される。**

要約上は同じに見えて、実際には**3つの別々の状況**があります。「空」はそのうち1つだけです。

| 実際は | 見分け方 |
| --- | --- |
| 一度もフォーマットされていない | 全バイトが `0xFF`。`analyzeBinary` が `contents: 'erased'` を返す |
| フォーマット済みで本当に空 | 構造（スーパーブロック、有効な NVS ページ）はあり、中身が無い |
| 中身はあるが読めない | 構造が無く、**かつ**バイト列が一様でない |

重要なのは3つ目です。NVS では暗号化されたパーティションがこう見えます。NVS 暗号化はフラッシュ暗号化とは別機能で、`nvs_keys` パーティションの鍵を使い、領域全体を暗号文にします。読めるページが無く高エントロピーなら、analyzer がその旨を報告します。

**フラッシュ暗号化は NVS を対象にしません。** チップが「暗号化 有効」と報告することで逆の結論を招きやすく、analyzer はまさにそれを警告します。

## ファイル一覧は出るが中身が壊れている

**正しいファイル名は出る。中のバイトが滅茶苦茶。**

SPIFFS のジオメトリ問題で、**失敗してくれるより厄介**です。

SPIFFS はページサイズとブロックサイズを自分では記録しないので推定が要ります。正しい値の約数である誤ったジオメトリは、**索引ヘッダには必ず当たる**ので正しいファイル名を全部見つけたうえで、誤ったオフセットからデータを組み立てます。実際のページサイズ 256 のイメージを 128 で読むと、正しい名前4つと壊れた中身4つが出てきます。

`parseSpiffs` は候補を「見つかったファイルが整合しているか」で採点するので、既定では起きないはずです。ジオメトリを明示した場合や `detectGeometry: false` を指定した場合は、判定に任せてみてください。

```js
const image = parseSpiffs(bytes);          // 判定あり
console.log(image.geometry);               // 何が選ばれたかをユーザーに見せる
```

FAT で同等の罠は wear levelling 層です。無視すると**ブートセクタは完璧に解析したうえで、FAT テーブルをルートディレクトリとして読みます**。`parseFat` は予備セクタを自動判定します。`{ wlDummySector: -1 }` はそれを止めるので、wear levelling 層が本当に無いイメージにのみ使ってください。

## NVS の書き込みが拒否される

**`buildNvs` が `NvsCapacityError` を投げる。**

データが収まっていません。デバイスが起動に使うパーティションを切り詰めるくらいなら拒否します。`error.details` に必要だった容量が入っています。

想像より容量を食うものが2つあります。

- **blob は 32 バイトごとに1エントリ。** 9000 バイトの blob は 285 エントリです。20KB のパーティション（126エントリ×5ページ、うち1ページは GC 用に確保されるので実質 504）では、**半分以上**を占めます
- **1ページは常に予約されます。** 全ページを使ったイメージはデバイスを「何も書けない」状態にするので、`buildNvs` はそれを作りません

本当に収まらないなら、答えは**安全マージンを削ることではなく、大きいパーティション**です。

**`RangeError: … does not fit the declared type`** は、値が型の範囲外という意味です（`U8` に 300 など）。値か型を変えてください。リファレンスアプリは build 時ではなく入力欄で弾くので、ユーザーは確認ダイアログを読む前に気づけます。

## ファイルシステムの再構築が拒否される・実機がマウントしない

**`FsCapacityError`。** ファイルが入り切っていません。不足はバイトではなく**ページ／ブロック／クラスタ単位**で報告します。実際に足りなくなったのがその単位だからです。ファイルを数バイト削っても普通は何も変わりません。SPIFFS のページはファイルの中身を251バイトしか持てず、LittleFS のブロックはどんなに小さいファイルでも1ファイル分を占めます。**ブロックサイズ4096で10バイトのファイルが100個あれば、必要なのは1KBではなく100ブロックです。**

SPIFFS は1ブロック、NVS は1ページを空けたままにします。理由は同じで、**空きの無いイメージはデバイスを「読めるが書けない」状態にする**からです。

**`FsPathError: SPIFFS has no directories …`。** SPIFFS は `/sub/nested.txt` を15文字の1個の名前として保存します。形式のどこにもディレクトリはありません。パス全体が31バイトに収まる必要があり、**空ディレクトリは存在のしようがありません**。構築前に `checkFsStore(store, 'spiffs')` を呼べば、どちらも先に指摘します。

**`buildFat needs the image the store came from`。** `source` を渡してください。パーティション末尾3セクタに wear levelling 層の状態が入っており、チップが乱数で決めたデバイスIDと、公開形式のどこにも定義のないチェックサムを含みます。引き継ぐことはできますが、作り直すことはできません。

**`build self-check failed: …`。** ビルダが自分の出力を読み直して一致しませんでした。これはあなたのデータではなく**このライブラリのバグ**です。可能ならイメージを添えて報告してください。デバイスには何も書かれていません。この検査が build の戻り値より前に走るのは、まさにそのためです。

**再構築は通ったのに実機がマウントしない。** 順に確認してください。

1. **パーティション全体を書きましたか。** 再構築は差分ではなく**完全なイメージ**です。既存のファイルシステムに一部だけ被せると、互換性のない前半と後半を持つことになります
2. **書き込み先は合っていますか。** `spiffs` という名前のパーティションに LittleFS イメージ、というのは実際によくある間違いです（arduino-esp32 の LittleFS は歴史的経緯でラベル既定値が `spiffs`）。この場合どちらとしてもマウントしません
3. **ジオメトリはファームウェアのビルド設定と一致していますか。** 再構築は元イメージのジオメトリを使います。`FsStore.from(...)` ではなく `new FsStore(...)` から組み立てた場合は既定値が使われます。とくに SPIFFS は自分のジオメトリを記録しないので、**デバイス側が食い違いに気づく手掛かりがありません**

どれでも説明がつかない場合は、このリポジトリの `tools/hardware-check.mjs --rebuild` が実機に対して一連の流れを実行し、**チップ自身のドライバが何を報告したか**を表示します。ホスト側からはそれ以上のことは分かりません。

**イメージにあったものが再構築後に消えている。** 再構築はコピーではなく**コンパクション**です。その形式が表現できないものは消えます。何が消えるかは `checkFsStore` が構築前に列挙します。更新日時は全形式で失われます。ファイルの中身の途中がゼロになっている場合は `store.incomplete` を見てください。そのファイルは**元から一部しか復元できておらず**、再構築でその欠損が確定しました。

## 全体的に遅い

4MB のダンプは 115200 で約6分、1500000 なら1分未満です。

stub を読み込んだ**後**に速度を上げてください（デバイスに速度変更を伝えられるのはその時点だけです）。そして信用する前に検証してください。

```js
await loader.loadStub();
await loader.changeBaudRate(460800);
```

**チップ内蔵 USB でも速度は効きます。** UART が挟まらないのだから無視されるだろう、と考えたくなりますが、ESP32-S3 と ESP32-P4 での実測では 256KB の読み出しが 115200 で 26 秒、1500000 で 3.4 秒 — **約8倍**でした。ここを飛ばさないでください。

速度の選び方は [guide.ja.md §11](./guide.ja.md#11-速くする) を参照。

## ブラウザでは動くが Node で動かない

違いは3つあり、3つとも本質的です。

1. **stub が取得できない。**（[上記](#stub-が読み込めない)）
2. **Transport が無い。** Node にシリアル API はありません。[transports.ja.md](./transports.ja.md) の5メソッドのインターフェースに対して書いてください。完全な実装例があります
3. **タイムアウトが読み出しを放棄してはいけない。** 手書き Transport で最も多い誤りで、症状（全ボードでチップ検出が失敗）は原因を全く指しません

`tools/hardware-check.mjs` が動作する Node 環境の実例です。読んでも走らせても構いません。ライブラリを実機に対して走らせて esptool のキャプチャと比較するので、**問題が自分側かリンク側かを切り分ける最短路**でもあります。

## それでも解決しないとき

誰かに尋ねる前に、これだけ集めてください。

- ログの内容。言い換えではなくエラーの `code`
- チップ、ボード、接続方法（直結 / ハブ / VM パススルー）
- 同じ操作で esptool が成功するかどうか
- 同じ領域を2回読んで一致するかどうか

1つ目と3つ目で、このページの大半は除外できます。
