# Changelog / 変更履歴

## Unreleased

## 1.1.0
- (EN) Documentation corrected against the shipped code. The spec still described a fixture policy the project reversed ("fixtures are generated in code"), an inspector with five tabs where there are two, a store shape from before the reconnect and staleness work, and a confidence scale that put a partition subtype at 0.3 when every shipped analyzer scores it 0.8–0.9. What happens to a region the partition table names but no parser reads — `coredump`, `phy`, and `nvs_keys`, which will never be read — was not written down anywhere; it is now [19](./docs/spec.md#19-handling-unsupported-regions).
- (JA) ドキュメントを実装に合わせて修正。仕様書には、プロジェクトが既に覆した fixture 方針（「fixture はコードで生成する」）、実際は2つしかない inspector のタブが5つ、再接続とデータ鮮度の対応より前の store 構造、および subtype を 0.3 とする confidence 基準（同梱の analyzer はすべて 0.8〜0.9 を返す）が残っていた。パーティションテーブルが名前を教えているがパーサが無い領域の扱い（`coredump` / `phy`、および恒久的に読まない `nvs_keys`）はどこにも書かれていなかったため、[19](./docs/spec.ja.md#19-未対応領域の扱い) として明文化した。
- (EN) The fixture provisioner now writes a core dump. `partitions.csv` gained a `coredump` partition — taken out of the unused second OTA slot, so every other partition kept its offset — and the sketch fills it by calling `abort()` once provisioning is done, then reports what ESP-IDF says about the dump on the boot after the panic. That is what made the parser below possible: the fixture comes off a device like every other one. `check-coredump.mjs` verifies it at the byte level and lists its strings, because it is the one fixture region holding RAM rather than constants this project chose. All three hardware-verified chips were re-provisioned from an erased state and re-captured, so every fixture now carries one.
- (JA) fixture プロビジョナがコアダンプを書くようになった。`partitions.csv` に `coredump` パーティションを追加し（未使用の第2 OTA スロットから確保したので、他のパーティションはオフセットもサイズも据え置き）、スケッチはプロビジョニング完了後に `abort()` してそれを埋め、panic 後のブートで ESP-IDF 自身の申告を報告する。これが下記のパーサ実装を可能にした。fixture が他と同じく実機由来で手に入るようになったためである。定数ではなく RAM を含む唯一の fixture 領域なので、`check-coredump.mjs` がバイトレベルで検証し、含まれる文字列を一覧する。実機検証済みの3チップすべてを消去状態から書き直して再取得したので、どの fixture にもコアダンプが入っている。
- (EN) Fixed: a FAT volume could lose a subdirectory without reporting anything. Working out which sector ESP-IDF's wear-levelling layer holds spare was decided by looking at the root directory alone, and on a board whose spare sector had moved along, "no shift at all" explains the root perfectly while putting every data cluster one sector out. Four of five files came back, no issue was raised, and nothing in the result said a directory was missing. The mapping is now chosen by whether it explains the whole tree — every subdirectory has to land on a directory too — and "no shift" is no longer indistinguishable from "could not work it out", which used to make a correctly parsed volume carry a warning. Three boards provisioned by the same sketch turned out to have their spare sector in three different places, so this was never going to be settled by one capture.
- (JA) 修正: FAT でサブディレクトリが黙って消えることがあった。ESP-IDF の wear levelling がどのセクタを予備にしているかの判定をルートディレクトリだけで行っていたため、予備セクタが移動したボードでは「シフト無し」がルートを完全に説明してしまい、その裏でデータクラスタが1セクタずれる。5個中4個のファイルが返り、issue は出ず、ディレクトリが欠けていることを示すものは結果のどこにも無かった。判定は**木全体を説明できるか**（サブディレクトリの飛び先もディレクトリであること）で選ぶようにし、あわせて「シフト無し」と「判定できなかった」を区別した（従来は正しく読めた領域にまで警告が付いていた）。同じスケッチで書いた3枚のボードで予備セクタの位置が3通りに割れており、1枚のキャプチャでは決着しない類の問題だった。
- (EN) Fixture capture no longer refuses a slow link. `capture.sh` searched rates down to 115200 only, probing each with a 256 KB read, and when none carried it reported that the problem was not speed. On two ESP32 boards over USB-UART bridges it was: neither could read 256 KB at any rate, and 38400 — below where the list stopped — carried 64 KB on both. The ceiling a bad link imposes turns out to be on bytes per transfer, and lowering the rate can raise it. The search now reaches 38400, quarters the probe when no rate carries it, and adopts the size that worked as the chunk size.
- (JA) fixture 取得がリンクの遅さで諦めなくなった。`capture.sh` の速度探索は 115200 が下限で、各候補を 256KB の読み出しで試し、どれも運べないと「速度の問題ではない」と報告していた。USB-UART ブリッジ経由の ESP32 2台では、それは速度の問題だった。どちらもどの速度でも 256KB を読めず、リストの下限より遅い 38400 では両機とも 64KB が通る。悪いリンクが課す上限は「1転送あたりのバイト数」の側にあり、速度を落とすとその上限が上がりうる。探索は 38400 まで届き、どの速度も運べない場合はプローブを 1/4 に縮め、通ったサイズをチャンクサイズに採用する。
- (EN) Fixed: a failed capture destroyed the fixture it was replacing. `capture.sh` truncated each region file before reading it, so a read that then failed left a 0-byte file where a good fixture had been — the worst outcome available to a tool whose whole job is producing those files, and hit twice on one marginal board. Regions are now assembled beside the destination and moved into place only when complete.
- (JA) 修正: 取得に失敗すると、差し替えようとした fixture のほうが壊れていた。`capture.sh` は各領域ファイルを読み出し前に切り詰めていたため、そのあと読み出しが失敗すると、正常だった fixture のあった場所に 0 バイトのファイルが残る。fixture を作るのが仕事のツールとして最悪の結果であり、リンクの悪いボード1台で2回踏んだ。各領域は隣で組み立て、完成したときだけ所定の位置へ移す。
- (EN) Fixed: the application told people to wait for releases that had already shipped. A region named by its partition subtype but not parsed — `coredump`, `phy`, `nvs_keys` — was reported as "planned for Phase 4", from a roadmap phase number the analyzer carried in its metadata. (`coredump` has since been implemented; see below.) Phases 2, 3 and 4 have all shipped, and `nvs_keys` was never going to be in any of them: without the eFuse key its contents are ciphertext, so there is nothing to read even in principle. `expectedPhase` is now `expectedStatus`, either `unplanned` or `never`, and the two get different sentences. **If you translate issue codes yourself:** an `nvs_keys` partition now reports `analyze.neverImplemented` where it used to report `analyze.notImplemented`, and `analyze.notImplemented` is left to `phy`. Also fixed alongside it: those sentences printed the format identifier rather than its name, so the text under a heading reading "PHY init data" said `phy-init`.
- (JA) 修正: アプリが「もう出たリリースを待て」と言っていた。パーティションの subtype から名前は分かるが解析はしない領域（`coredump` / `phy` / `nvs_keys`）を「Phase 4 で対応予定」と表示していた。analyzer がメタデータにロードマップの Phase 番号を持っていたためである（`coredump` はその後実装した。下記参照）。Phase 2 / 3 / 4 はいずれも完了しており、しかも `nvs_keys` はそのどれにも入る予定が無かった。eFuse の鍵が無ければ中身は暗号文で、原理的に読むものが存在しない。`expectedPhase` を `expectedStatus`（`unplanned` / `never`）に置き換え、両者で別の文面を出す。**issue code を自前で翻訳している場合は注意:** `nvs_keys` パーティションが返すコードが `analyze.notImplemented` から `analyze.neverImplemented` に変わり、`analyze.notImplemented` は `phy` 専用になった。あわせて修正: その文面が形式の表示名ではなく識別子を出しており、見出しが「PHY 初期化データ」なのに本文は `phy-init` になっていた。
- (EN) **Core dumps are now parsed** ([13](./docs/spec.md#13-core-dumps)). `parseCoreDump` reads the panic reason, the task that crashed, and every task's name, program counter, stack pointer and captured stack, plus the exception registers on Xtensa and the SHA-256 prefix of the build that produced the dump. It is only the third format here that reaches confidence 1.0, because it carries both a magic and a CRC-32 that verifies — and the analyzer ignores the partition subtype entirely, so a dump lifted out of a flash image or opened as a bare file gets the same answer. The inspector shows all of it; the Hex tab labels the header, each note, each TCB and each stack.
- (JA) **コアダンプの解析に対応**（[13](./docs/spec.ja.md#13-コアダンプ)）。`parseCoreDump` が panic 理由、クラッシュしたタスク、各タスクの名前・プログラムカウンタ・スタックポインタ・取得済みスタックを読み、加えて Xtensa では例外レジスタ、そのダンプを出したビルドの SHA-256 先頭部分も返す。マジックと検証可能な CRC-32 の両方を備えるため、confidence 1.0 に到達する3つ目の形式になった。analyzer はパーティションの subtype を一切見ないので、フラッシュイメージから切り出したダンプも単体ファイルとして開いたダンプも同じ答えになる。inspector はその全部を表示し、Hex タブはヘッダ・各ノート・各 TCB・各スタックにラベルを付ける。
- (EN) Two things the core dump work turned up that are not in the header documentation. The header is **not** a fixed 24 bytes: four lengths are in circulation across the format's versions, the version word is the only thing that says which one is in front of you, and reading a 20-byte header as 24 puts the ELF magic four bytes out — a working device would look like unreadable data. And the task name has no fixed offset in a FreeRTOS TCB, because `configMAX_TASK_NAME_LEN` and the MPU wrappers move it; rather than hard-code the 52 that three Arduino cores happen to share, the offset is derived from the one position where *every* captured TCB holds a NUL-terminated string, and where no such position exists the tasks go unnamed. One wrong task name is worse than none.
- (JA) コアダンプの実装で判明した、ヘッダの文書に書かれていないことが2つ。ヘッダは 24 バイト固定**ではない**。この形式のバージョン群には4種類の長さが流通しており、どれかを教えるのはバージョン語だけで、20 バイトのヘッダを 24 バイトとして読むと ELF のマジックが4バイトずれる。正常なデバイスが「読めないデータ」に見える壊れ方をする。もう1つ、FreeRTOS の TCB においてタスク名の位置は固定ではない。`configMAX_TASK_NAME_LEN` や MPU ラッパで動くためである。3つの Arduino コアがたまたま共有している 52 を決め打ちせず、**取得できたすべての** TCB で NUL 終端文字列が始まる唯一の位置として導出し、そういう位置が無ければタスクは無名のままにする。1つ間違ったタスク名は、名前が無いことより悪い。
- (EN) A core dump whose checksum does not match is still shown, with the mismatch reported and confidence dropped to 0.5: whoever is looking at one has a device that already went wrong, and withholding the task list because a byte moved takes away the only record of what it was doing. The SHA-256 variant of the format is reported as *unverified* rather than as valid or as broken — the only SHA-256 available in a browser is asynchronous, and an async parser would infect every caller for a build option that is off by default.
- (JA) チェックサムが合わないコアダンプも、不一致を報告し confidence を 0.5 に下げたうえで内容を表示する。それを見ている人のデバイスは既に異常を起こしており、1バイトずれたからといってタスク一覧を出さないのは、何をしていたかの唯一の記録を取り上げることになる。この形式の SHA-256 版は「有効」とも「壊れている」とも言わず**未検証**と報告する。ブラウザで使える SHA-256 は非同期のものだけで、既定では無効なビルドオプションのために parser を非同期化すると呼び出し側すべてに波及するためである。
- (EN) Backtraces are deliberately out of scope, and the parser says so rather than leaving a column of bare numbers unexplained. Turning an address into a function name needs the ELF of the exact build that crashed; no dump carries it, which is why Espressif's own tool hands the application ELF to GDB. What the dump does carry is which build it was, so the addresses can be resolved elsewhere.
- (JA) バックトレースは意図的に対象外とし、生の数値の列を説明なしに残すのではなく、その旨を明示する。アドレスを関数名に直すにはクラッシュしたまさにそのビルドの ELF が必要で、それはどのダンプにも入っていない。Espressif 自身のツールがアプリの ELF を添えて GDB を呼ぶのはそのためである。ダンプが持っているのは「どのビルドか」の情報なので、解決自体は外部で行える。

## 1.0.0
- (EN) First release. A dependency-free, build-step-free JavaScript library for reading, analysing, editing and writing ESP32 flash — the serial bootloader protocol, the flasher stub, partition tables, firmware images, otadata, NVS, SPIFFS, LittleFS and FAT — plus a Web Serial reference application. Runs from a `<script type="module">` or from Node; `esp-flashjs/core` is the parsers alone, with no serial code.
- (JA) 初回リリース。依存もビルド手順も不要な JavaScript ライブラリで、ESP32 のフラッシュを読み・解析し・編集し・書き戻す。シリアルブートローダのプロトコル、flasher stub、パーティションテーブル、ファームウェアイメージ、otadata、NVS、SPIFFS、LittleFS、FAT に対応し、Web Serial のリファレンスアプリを同梱する。`<script type="module">` からも Node からも動き、`esp-flashjs/core` はパーサのみでシリアル関連を含まない。
- (EN) Everything is verified against ESP32, ESP32-S3 and ESP32-P4 hardware, and the test fixtures are **bytes those devices wrote** rather than bytes this project generated. That distinction is the reason this release exists: a parser and the fixture it is tested against, written from the same reading of a format, agree with each other whether or not that reading was correct. Nine faults survived a complete, passing test suite until real captures replaced the generated ones.
- (JA) すべて ESP32 / ESP32-S3 / ESP32-P4 の実機で検証しており、テスト fixture は**実機が書いたバイト列**であって、このプロジェクトが生成したものではない。この区別こそがこのリリースの理由である。同じ形式理解から書かれたパーサと fixture は、その理解が誤っていても互いに一致してしまう。実機キャプチャに置き換えるまで、**全部通っているテストスイートを9件の不具合が素通りしていた**。
- (EN) Flash operations: chip detection, stub upload, chunked reads with per-chunk retry, write, erase, device-side verify and whole-chip dump. Operations on one link are serialised — two started at once each read the other's frames, which presents as a checksum mismatch, then timeouts, then a device that appears to have stopped responding.
- (JA) フラッシュ操作：チップ検出、stub 転送、チャンク分割＋チャンク単位リトライの読み出し、書き込み、消去、デバイス側検証、チップ全体のダンプ。1本のリンク上の操作は直列化される。2つ同時に始めると互いのフレームを読み合い、チェックサム不一致 → タイムアウト → 「デバイスが応答しない」という、ケーブル不良と区別のつかない症状になる。
- (EN) NVS is parsed, edited, rebuilt and diffed. `buildNvs` re-reads its own output and compares it against the store before returning, and refuses rather than truncating — a partition a device has to boot from is the wrong place to silently drop the last entry.
- (JA) NVS は解析・編集・再構築・差分に対応。`buildNvs` は返す前に自分の出力を読み直してストアと突き合わせ、入り切らなければ切り詰めずに失敗する。デバイスが起動に使うパーティションは、最後のエントリを黙って落としてよい場所ではない。
- (EN) SPIFFS, LittleFS and FAT are parsed and rebuilt at the geometry they came from. Each is pinned by a check the round trip cannot fake: SPIFFS is read back through its object indexes the way a device reads it, LittleFS is walked along the tail chain its block allocator follows, and FAT carries ESP-IDF's wear-levelling state over rather than regenerating it. `tools/hardware-check.mjs --rebuild` settles the remaining question by writing an edited image back and reading the chip's own driver report.
- (JA) SPIFFS / LittleFS / FAT は解析と、元と同じジオメトリでの再構築に対応。各形式に**ラウンドトリップでは誤魔化せない検査**を用意した。SPIFFS はデバイスと同じくオブジェクトインデックス経由で読み戻し、LittleFS はブロックアロケータが辿る tail チェーンを歩き、FAT は ESP-IDF の wear levelling 状態を再生成せず引き継ぐ。残る「実機がマウントするか」は `tools/hardware-check.mjs --rebuild` が、編集したイメージを書き戻してチップ自身のドライバの報告を読むことで確認する。
- (EN) Analysers recognise and describe a region, and third-party formats can register their own at runtime ([docs/analyzers.md](./docs/analyzers.md)). Encryption is reported from what the chip says about itself, not from entropy: an unencrypted LittleFS image holding a counter file scores a perfect 8.0 bits per byte.
- (JA) Analyzer が領域を認識して内容を記述し、独自形式は実行時に登録できる（[docs/analyzers.ja.md](./docs/analyzers.ja.md)）。暗号化の判定はエントロピーではなくチップ自身の申告による。カウンタを持つ**暗号化していない** LittleFS イメージが 8.0 bits/byte ちょうどを記録するためである。
- (EN) The reference application at [tanakamasayuki.github.io/esp-flashjs](https://tanakamasayuki.github.io/esp-flashjs/) has a flash map, an inspector with analysis and a hex view, an NVS editor, a filesystem tree with add/replace/delete/in-place text editing and ZIP extraction, a link-speed control, and en / ja / zh-Hans / zh-Hant.
- (JA) リファレンスアプリ（[tanakamasayuki.github.io/esp-flashjs](https://tanakamasayuki.github.io/esp-flashjs/)）はフラッシュマップ、解析と hex ビューを持つ inspector、NVS エディタ、追加／置換／削除／その場でのテキスト編集と ZIP 取り出しができるファイルツリー、通信速度セレクタを備え、en / ja / zh-Hans / zh-Hant に対応する。
- (EN) Nothing read from a device outlives a connection, and a write downloads a backup before touching anything. Both follow from the same rule: a copy of flash goes stale the moment the application starts running again, and the tool must not present a stale copy as the current one.
- (JA) デバイスから読んだものは接続をまたいで残らず、書き込みは何かに触れる前にバックアップをダウンロードする。どちらも同じ規則から出ている。**フラッシュのコピーはアプリケーションが動き出した瞬間に古くなる**のであり、古いコピーを現在のものとして見せてはならない。
- (EN) Limits: rebuilding regenerates at the original geometry and does not format to arbitrary parameters; an encrypted region is detected but [deliberately not decrypted](./docs/spec.md#95-decryption-deliberately-not-implemented); the other chips in the table are implemented but not hardware-verified, and the README says which is which.
- (JA) 制限：再構築は元のジオメトリでの再生成に限られ、任意パラメータでのフォーマットはしない。暗号化領域は検出するが[意図的に復号しない](./docs/spec.ja.md#95-復号-意図的に実装しない)。表にある他のチップは実装済みだが実機未検証であり、README にどれがどちらか明記してある。
