# Hardware fixtures

**English** · [日本語](./README.ja.md)

Everything needed to provision a device with known contents, dump its flash,
and commit the result as a test fixture.

---

## Why this exists

Every parser bug found so far **passed the test suite**. The reason was always
the same: the fixtures were generated by the code under test, so a wrong
constant agreed with itself.

| Bug | Why the tests missed it |
| --- | --- |
| Partition magic byte order | parse and build shared the same wrong constant |
| otadata CRC convention | the fixture's CRC used the same wrong formula |
| Checksum scope on data commands | the mock never verified checksums |
| READ_FLASH ack not SLIP-framed | the mock ignored acknowledgements |
| Abandoning a timed-out read | the mock answered synchronously |

**Only bytes that came off a real device break that complicity.**

Everything written is a fixed constant chosen here, so nothing secret is
involved. The MAC address lives in eFuse and is not in any captured region. The
output is safe to commit.

---

## What you need

- An ESP32-family board with at least 4 MB of flash
- Arduino IDE with arduino-esp32, or arduino-cli
- `esptool` (`pip install esptool`)

**The contents are erased.** Do not run this on a board holding anything you
want to keep.

---

## Steps

### 1. Flash the sketch

Open `fixture_device/fixture_device.ino` in the Arduino IDE.

- **Board**: your chip
- **Partition Scheme**: `Custom` — the `partitions.csv` beside the sketch is
  picked up automatically

With arduino-cli:

```sh
cd tools/fixture-device
arduino-cli compile --fqbn esp32:esp32:esp32 \
  --build-property build.partitions=partitions \
  --build-property upload.maximum_size=1310720 fixture_device
arduino-cli upload --fqbn esp32:esp32:esp32 -p /dev/ttyUSB0 fixture_device
```

### 2. Wait for it to finish

Open the serial monitor at 115200 and wait for **`FIXTURE COMPLETE`**.
Capturing early bakes a half-written state into the fixture.

### 3. Capture

**Close the serial monitor first** — a held port makes the read fail.

```sh
PORT=/dev/ttyUSB0 ./tools/fixture-device/capture.sh
```

The chip is detected automatically and the files land in
`test/fixtures/hardware/<chip>/`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | required | Serial port |
| `CHIP` | auto-detected | Force `esp32`, `esp32s3`, `esp32p4`, … |
| `BAUD` | `921600` | Lower to `115200` if reads fail |
| `OUT` | `test/fixtures/hardware/<chip>/` | Output directory |

For several boards in a row:

```sh
PORT=/dev/ttyUSB0 ./tools/fixture-device/capture.sh   # ESP32
PORT=/dev/ttyACM0 ./tools/fixture-device/capture.sh   # ESP32-S3
PORT=/dev/ttyACM1 ./tools/fixture-device/capture.sh   # ESP32-P4
```

## What gets captured

| File | Contents | What it pins down |
| --- | --- | --- |
| `bootarea.bin` | `0x0`–`0x8000` | The bootloader image; its start offset differs per chip |
| `partition-table.bin` | `0x8000` | Entry magic byte order, MD5 |
| `nvs.bin` | 20 KB | Every type, split blobs, overwrites, deletes, page spill |
| `otadata.bin` | 8 KB | The ROM CRC convention. With no factory partition the bootloader really does write this |
| `app0.bin` | 1.25 MB | Image header, segments, SHA-256, app description |
| `app1.bin` | 1.25 MB | Unwritten, so erased flash has a reference too |
| `spiffs.bin` | 320 KB | SPIFFS |
| `littlefs.bin` | 320 KB | LittleFS |
| `ffat.bin` | 832 KB | FAT with wear levelling |
| `MANIFEST.txt` | — | Chip, timestamp, esptool version, sha256 of each file |

`app0.bin` and `app1.bin` are 1.25 MB each. app0 is the compiled sketch and
therefore depends on your toolchain, so **decide separately whether to commit
it** — the first 64 KB is enough to exercise image parsing.

## What goes into NVS

Chosen to hit the parts of the format that are easy to get wrong.

| Namespace | Contents | Purpose |
| --- | --- | --- |
| `types` | u8/i8/u16/i16/u32/i32/u64/i64/string/empty string | Every type code, and signedness |
| `blobs` | `small` (64 B) | A blob that fits one chunk |
| | `big` (9000 B) | **Over 4032 B, so IDF splits it into a BLOB_IDX plus several BLOB_DATA chunks** |
| | `rewritten` | An overwrite: the old entry stays, marked erased, and the sequence number decides |
| | `deleted` | A delete: only the erased entry remains |
| `many` | `k000`–`k199` | More than 126 entries, so pages spill and one reaches FULL |

---

## What goes into the filesystems

All three get the same tree, so results can be compared across formats.

```
/hello.txt      a short text file
/big.bin        4096 bytes, larger than one page
/sub/nested.txt a nested path
/empty.txt      an empty file
```

Some formats are unavailable on some chips or partition sizes. The sketch prints
`unavailable` and carries on; capture whatever worked. FAT in particular needs a
wear-levelling layer and will not fit a small partition.

---

## Before committing

1. Read `MANIFEST.txt`
2. Check the sizes look right — all 0xFF means the write did not take
3. Commit the whole `test/fixtures/hardware/<chip>/` directory

When you replace a fixture, update the tests that depend on it. **Do not adjust
the expectations to match the implementation's output** — the device's bytes are
the authority, not ours.
